# 工具执行与自动审查

2026-10-07：Chili 的工具执行只保留 `full-access`（完全访问）和
`auto-review`（自动审查），取代旧的规则与人工审批机制。

## 用户配置

首次启动默认使用自动审查。完全访问直接执行工具；自动审查由宿主调用一个
独立、无工具的模型请求，判断当前操作是否符合用户意图和审查说明。
用户可以在桌面设置中修改审查说明、恢复默认说明，以及选择审查模型。
没有单独选择模型时，审查请求沿用当前任务的模型选择，但不共享其推理过程。

个人配置保存在 `<CHILI_HOME>/review-settings.json`（通常为
`~/.chili/review-settings.json`），包含 `profile`、`reviewInstructions` 和可选的
`reviewerModel: { provider, model }`。设置更新立即作用于当前 Host 内的会话，
并成为后续 Host 的默认值。已经打开的其他 Host 不会自动热加载这个文件。
CLI 的 `--yes` 为当前进程选择完全访问。

旧 `[permissions]` 配置不再参与执行，也不会自动转换成审查说明。
不再提供本次／会话／项目／永久允许、工具和路径的允许规则、人工审批按钮。
审查说明用于表达用户的判断标准；代码风格仍属于主模型的工作要求。

## 执行链

1. 工具执行器校验并固定实际参数、工具定义和资源身份。
2. 执行器调用宿主的 `ToolExecutionGate`，传入完整参数、调用身份、工作目录、
   工具说明和资源描述。`code_mode` 中的每个子调用也经过这一入口。
3. 完全访问跳过全部模块的审查能力，返回仍需复核的本次许可。自动审查通过
   必装的 `chili.execution-review` 模块，把具体动作、带来源的任务上下文和
   用户审查说明交给独立模型；之后依次运行扩展模块的审查能力。
4. 模型必须返回 `{ "decision": "allow" | "deny", "reason": "…" }`。
   拒绝理由作为工具失败反馈交回主模型。调用失败、超时、无效输出也阻止执行，
   但保留系统错误与审查拒绝的区别。
5. 自动审查只有在全部能力允许时才能执行；任一拒绝立即结束，后续允许不能
   覆盖它。真正执行前以及等待资源锁后，再检查调用与所有许可是否有效。
   设置或相关用户上下文改变后，旧许可不能继续放行。完全访问切换为自动审查
   也会使原许可失效。重新检查不会重复请求审查模型。

批准只属于这次具体调用，不积累成授权规则。结果记录在工具事件的 `review`
元数据中。原来的 `approval()` 描述改名为 `resources()`，只用于资源身份、
快照和委派范围；它不决定是否调用审查器。

宿主通过[模块化 Hook](../packages/host/hooks.md)装配审查能力。一个 `HostModule`
可以同时提供多种能力；内置执行审查模块既提供 `prompt.collect` 审查说明，也提供
`tools.review` 判断。`ToolExecutionGate` 是执行器调用这个能力的强制适配边界，
不是另一个隐藏的 reviewer。Host 构造时要求正式内置审查模块存在，扩展不能用
自己的 `allow` 替代它，也不能修改审查后的参数。

模块清单在构造时固定，根与子 Agent 共用。扩展可以增加 `tools.review` 约束；
提示词贡献、结果处理和生命周期观察本身没有放行权限。这个内部 TypeScript
接口没有脚本插件加载器或 `next()` 中间件，也没有让主模型主动调用审查的工具。

可等待模块能力默认每次限时 30 秒，可配置到 60 秒。内置审查模块使用 60 秒，
审查服务的 `reviewTimeoutMs` 同时生效，以先到的截止时间为准。超时和基础设施
错误都不执行工具；它们与模型明确拒绝保留不同的错误来源。

## 结果与观察边界

工具执行后，`tools.processResult` 可以处理 `title`、`output` 和 `content`，
不能改变规范化结果中的 `structuredData`、`metadata`、`artifactIds`。
原始结果与 sidecar 只处理一次，工具完成事件保留原始审计输出。处理失败不会
隐去真实执行已成功的事实，也不能成为自动重跑副作用的依据。

模型生命周期通过 `purpose: "review"` 区分审查请求，同时保留发起会话的
`agentRole: "root" | "child"` 和子会话的父级身份。内部模型流观察不会把审查
内容自动写入公开运行事件、SSE 或会话历史，也不改变 provider 的重试策略。
同步观察者异常只停用该模块的对应观察能力，不会卸载同一模块的 `tools.review`。

## 上下文和执行边界

审查器使用宿主记录的用户输入来源区分人类指令、代理消息、命令展开内容、
工具结果和用户问题的回答。工具参数或代理自述不能自行声称获得人类授权。
上下文经过有界选择，并明确标注缺失；实际工具参数不会被静默截断后批准。

自动审查的普通命令通过后可以正常执行，不需要模型另外请求沙箱提权。
参数校验、工具版本一致性、取消、文件观察与委派给子代理的范围约束继续存在。
审查是模型判断，不等于操作系统隔离，也不保证永不误判。

这次模块化没有把审查升级成调查 Agent。审查请求仍无工具，只能使用宿主提供的
动作和证据。增加只读调查能力需要另行定义证据范围、预算和失败策略，现有文档
不承诺它已启用。

旧审批事件和数据库记录保留，用于读取历史。恢复被中断的旧执行时，会关闭
孤立的待审批记录，要求新的工具调用重新经过执行链，不恢复旧的人工授权。

## 验证方式

使用可控的假审查模型验证允许、拒绝、异常、取消、超时、并发设置变化、
上下文来源、嵌套调用和 MCP 完整参数；用真实临时文件与本地进程验证执行效果。
仓库全量测试、类型检查和 smoke gate 检查各端接线。
这些检查验证软件行为，不代表对某个审查模型判断能力的评测。
